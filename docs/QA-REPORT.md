### 4.1 🟡 中低 · 组 bbox 为 0 时没有告警（第一轮遗留，未修）

**位置**：`src/psd/ir-builder.js:234` 附近

**第一轮我写过这个问题，本轮复查仍在**：
```js
// 空组的 bbox
l.bbox = {"x":0,"y":0,"w":0,"h":0}
l._derive = {"usedChildren":0,"skippedChildren":0}
针对该层的 warnings 数 = 0     ← 无告警
```
**告警覆盖不对称**：
- **叶子层** bbox 为 0 →有 `EMPTY_LAYER` 告警（`ir-builder.js:226` 的分支）
- **组** bbox 为 0 → **无任何告警**

**根因与 BUG#1 同源**：代码里「组」走独立分支（`if (type === 'group') {...} else {...} `），
告警逻辑只写在 `else`（叶子）分支里，组分支没有对应处理。

**影响**：
- 画师建了一个空组，或一个「所有子层都零尺寸/隐藏」的组
- `design_ir.json` 里该组 `bbox={0,0,0,0}`
- 小 Q 需要主动去看 `_derive` 才知道「这个组的 bbox 是空的、是推导不出内容」
- **L2 尺寸校验遇到这个组会静默失准**（和 BUG#1 同类的静默路径）

**为什么我判中低而非高**：
- `_derive` 字段**确实存在且可读**，人能看到原因（不是完全不可见）
- 黄金样本里6 个组**全部 bbox 非 0**，没有实际触发
- 不像 BUG#1 那样「数值错」，而是「该报警没报」

**修复建议**：在组分支补对称告警：
```js
if (node.bbox.w === 0 || node.bbox.h === 0) {
  warnings.push({
    code: 'EMPTY_LAYER', layer: id,
    msg: `组图层『${node.name}』(${derived.used} 个子层参与、${derived.skipped} 个被跳过)`
       + '并集仍为零尺寸 —— 该组可能为空组，或所有子层都是零尺寸/隐藏图层，请人工确认',
  });
}
```

### 4.2 🟡 中低 · `validateComposite` 对单色图误报

见 §3.4 完整实测。

**位置**：`src/report/ir-overlay.js:133`
```js
if (stats.distinctColors <= 1) {
  return { usable: false, reason: `合成预览图只有 ${stats.distinctColors} 种颜色...` };
}
```

**问题**：「只有 1 种颜色」**不等于**「退化」。合法的一色图确实存在：

- PSD 规格样例、纯色弹窗底
- 只有 1 个可见图层的极简稿

**但真实 PSD 常见形态（底+按钮=2色）不误报**，所以实际触发面窄。

**修复建议**：把「退化判据」与「信息量不足判据」分开——

### 4.3 🟢 低 · net-guard 守卫对 `http2` / `dgram` 只报 warn

**位置**：`src/core/net-guard.js`

```
http / https / net / dns / tls / child_process / worker_threads  → ERROR 拦截 ✅

dgram / inspector / repl / vm / module / cluster / http2       → 仅 warn ⚠
```

`dgram`（UDP，能发包）都具备真实出站能力，**应为 error 级**。
当前只报 warn，且 `assertNoNetwork` **不把 warn 当失败**（我实测 `src/` 有 1 条 warn 仍通过）。

**这一条我认为影响有限**：warn 级 + 顶部报告仍会显示，人能看见。
但**从合规红线角度，能出站的模块应该是 error**。

**我实测的 warn 内容是安全的**：

```
      const mod = require(entry.module);
```
我追查了 `entry.module` 的来源 —— 是 `COMMANDS` 表里的**硬编码字面量**

**要求**：P1 交接时把「细长条纹/细长椭圆误判为可切」明确列为已知限制，

### 4.5 关于「判据对描边宽度敏感」—— 观察成立，但比工程师描述的更好

他诚实说明「你那份描边宽高比不同仍落 NEVER」。
**我做了完整的宽度扫描（9 档），结论要修正他的描述**：

| 描边宽度 | 判定 | radial |
|---|---|---|
| 1px | CAN_9GRID ✅ | 0.000 |
| **2px** | **NEVER** ⚠️ | **0.600** |
| 3px | CAN_9GRID ✅ | 0.981 |
| 4px ~ 20px | CAN_9GRID ✅ | 1.000 |

**关键发现：不是「越粗越 NEVER」，而是「2px 是孤立异常点」** ——
2px 描边的 `radial=0.600` 恰好落在判定阈值附近，其余宽度都 ≥0.98被正确判为 CAN_9GRID。

**所以他的修复比我第一轮观察到的更有效**：
- 我第一轮用的是「2px 描边 + 100x60 宽高比」，落 NEVER
- 他用自己的 3px fixture 测是 CAN_9GRID
- 我用他的修复 + **他自己的宽高比（140x90）+ 3px** 复测 → **CAN_9GRID ✅**

**真实素材风险评估**：
- 1-4px 描边（UI 最常见）→ 全部正确判 CAN_9GRID
- **唯一风险窗口是 2px 左右的细描边**（`radial` 在 0.6 附近）
- 粗描边/3D 边框 → 反而能正确判
- **结论：比工程师自己描述的乐观，真实素材大面积出问题的概率低。**
