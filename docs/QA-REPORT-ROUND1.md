## 2. BUG 清单（按严重程度排序）

### 🔴 BUG #1 · 严重 · 嵌套组 bbox 静默错误

**位置**：`src/psd/ir-builder.js:52-84`（`deriveGroupBox`）

**事实**：`deriveGroupBox` 的文档注释写着
> 「子层是组 -> 递归（同样不用组自身坐标）」

但**实现里没有任何递归调用**。当子层本身是组时：
1. `child.bbox` 不存在 → 调`boxOfLayer(child)`
2. `boxOfLayer` 读组自身的 `left/top/right/bottom` —— 恒为 `0,0,0,0`
3. `w<=0` → `skipped++`，**整个子组被丢弃**

结果：**一个组的 bbox 只包含它的叶子孙层，不包含它的子组后代**。

**复现步骤**（我实测的最小案例）：
```js
const { deriveGroupBox } = require('./src/psd/ir-builder');
deriveGroupBox([
  { name: '内层组', children: [{ left: 0, top: 0, right: 10, bottom: 10 }] },
  { left: 500, top: 400, right: 520, bottom: 420, name: '独叶' },
]);
```
**期望**：`{x:0, y:0, w:520, h:420}`
**实际**：`{x:500, y:400, w:20, h:20}`（内层组被跳过，`skipped:1`）

**为什么工程师的 16 条测试没抓到**：
他的黄金样本 `state_A.psd` 里，`弹窗框架 > 组 1200 > {矩形1, 边框光}`，
而 `弹窗框架` 的**另一个子层 `矩形11` 是 480×320 的全幅底框**，
`组 1200` 的两个子层（8px 高的横条）完全落在它内部。
于是无论 `组 1200` 参与不参与并集，`弹窗框架` 的结果都一样 —— **bug 被fixture 结构掩盖**。
我独立手写递归并集算法对账他的黄金样本，3 个组全部一致，**所以他的测试全绿**。
但这只是运气：真实 PSD 里只要出现「子组比兄弟节点更外扩」或「子组是唯一来源」，bbox立刻偏小。

**影响**（静默、不报错）：
- `design_ir.json` 里组的 `w`/`h` 偏小 → **L2尺寸校验全线失准** → RESIZE/MOVE 误判
- `positionTolerance` / `IoU` 全部偏移
- `ir_overlay.html` 的 bbox 框画错 → **人工核对时看错了以为是准的**
- 组 bbox 是「父容器尺寸」，FGUI 里直接决定组件实际大小 → **可能生成错误尺寸的组件**

**修复建议**：
```js
function deriveGroupBox(children, ctx) {
  // ... 循环内改为：
  for (const child of children || []) {
    let box;
    if (child && Array.isArray(child.children)) {
      // 子层是组：递归求它的并集，绝不读组自身坐标
      box = deriveGroupBox(child.children).box;
    } else {
      box = child.bbox || boxOfLayer(child);
    }
    // ... 后续不变
  }
}
```
**必须补的回归测试**：一个「子组比所有兄弟节点都更外扩」的结构 ——
这是唯一能暴露该bug 的形状，而当前 fixture 里一个都没有。

### 🟠 BUG #2 · 严重 · 合成图全黑，`ir_overlay.html` 底图不可用

**位置**：`src/psd/canvas-shim.js`（shim 的合成路径）+ `src/psd/reader.js:91`

**实测数据**（我独立跑的，不是复述工程师的话）：
```
读回 state_A.psd 的合成图：720x560
RGB 非黑像素: 0 / 403200  (0.00%)
alpha 非零:  403200 / 403200 (100.00%)
不同颜色数:  1     唯一颜色 = (0, 0, 0, 255)
```

**合成图是一张纯黑不透明图**。原因：shim 提供了 `createImageData`，
所以 ag-psd 走 `useImageData:true` 路径；但 shim 的合成实现没有把图层的imageData
真正 blit 到画布上，只是把画布初始化成不透明黑。

**为什么工程师的测试是绿的**（这是本报告最重要的发现之一）：
`test/unit/canvas-shim.test.js:110` 的断言是
```js
if (comp.data[i + 3] !== 0) { nonZero++; ... }   // 只看 alpha 通道
assert.ok(nonZero > 0, '合成图 alpha 通道不应全为 0');
```
**纯黑不透明图的 alpha 恰好全为 255**，所以这个断言**必然通过**。
这是典型的「断言了非空壳，没断言正确性」。

**下游影响**：
- `ir_overlay.{A,B}.html` 是 R2-F6 交付物，**其唯一用途就是人工核对 bbox 叠在效果图上**
- 我解码了 `ir_overlay.A.html` 内嵌的 PNG：**506 字节，0/403200 非黑像素**
- 小Q 打开这个文件看到的是一张**纯黑底图 +彩色 bbox 框**，框的位置对不对他无从判断
- **这等于把人工校验手段本身搞坏了**，而且坏得「看起来正常」（HTML 能开、框能画）

**对比：图层路径是好的**。我用自己的 PSD 做逐像素往返验证：
```
写入 (x,y) 的期望值 = (x*30+5, y*60+7, x*y, 255)
读回差异样本: 无     ← 8x4x4 = 128 个通道全部精确一致
半透明 alpha (0,1,128,255) 精确保留✅
```
所以 shim 的**图层**路径是可信的，只有**合成**路径坏了。

**修复建议**：
- 在 shim 的合成函数里真正实现 `putImageData` / `drawImage` 的像素合成
  （工程师的注释说实现了「source-over 合成」，但实测没生效，需复查）
- 或者：若合成图不可靠，`ir-overlay.js:89-92` 应**显式警告**「底图不可用，仅显示 bbox」，
  而不是把一张纯黑图当有效底图嵌进去 —— **静默给错东西比明确报错的危害大**
- **必须补的断言**：至少 1 条「合成图 RGB 通道非全零」+ 1 条「已知像素值往返一致」

### 🟡 BUG #3 · 中等 · 渐变面板 / 描边面板被误判为 NEVER

**位置**：`src/imaging/grid9.js`档 1 与档 4

我用**自己造的形态**（不是工程师的 25 张）实测，25 条中18 条符合预期、7 条不符。
其中**误判方向全部是「该给 CAN_9GRID 却给了 NEVER」**：

| 形态 | 期望 | 实得 | 命中档位 | 特征值 |
|---|---|---|---|---|
| **横向渐变面板** 160x50 | CAN_9GRID | ❌ NEVER (conf 0.4) | 档 5 空白区 | `midRowVar=0.241 > 0.15` |
| **竖向渐变面板** 60x140 | CAN_9GRID | ❌ NEVER (conf 0.4) | 档 5 空白区 | `midColVar=0.241 > 0.15` |
| **描边面板** 100x60 | CAN_9GRID | ❌ NEVER (conf 0.9) | 档 1 放射 | `radial=1.000 > 0.88` |
| **斜面浮雕按钮** 90x34 | CAN_9GRID | ❌ NEVER (conf 0.9) | 档 1 放射 | `radial=0.919 > 0.88` |
| 1x1 白 / 8x8 纯色 | NEVER | ❌ CAN_9GRID | — | 极小图退化 |

**根因分析**（我做了特征归因，不是猜的）：
- `flatMidVarianceMax: 0.15` 是**对合成数据标的**。真实 UI 面板几乎都有渐变，
  而渐变必然让中行/中列方差超阈值 → 全部落入档 5 空白区
- `radialSymmetry > 0.88` 的档 1 会把**任何带矩形描边的图**判成放射纹理 ——
  矩形边框的四条边在扇区统计里天然形成「角度方向上的高频跳变」，
  特征把「矩形描边」和「放射纹」混为一谈了

**严重程度评估：低（不构成事故）**。
按项目「不确定返 NEVER」的成本不对称哲学，**误判 NEVER 是安全侧**（人工手切 10 秒），
不会造成线上事故。所以这不是阻断性bug，**但会严重削弱工具价值** ——
真实素材里最常见的面板形态全部需要人工处理，等于工具没干活。

**修复建议**：
1. 档 1（放射）判定前先排除「矩形描边」：若 `edgeDensity` 高但角向能量集中在
   0°/90°/180°/270° 四个方向，应识别为矩形框而非放射纹
2. 档 4 的平坦度阈值应对**单调渐变**放行：渐变的方差沿单一方向单调变化，
   与「无序高频噪声」的方差分布形态不同，可用「一阶差分同号率」区分
3. 极小图（< 8x8）应直接返 NEVER，不做形态判定

**注意**：这需要**真实素材**重新标定阈值，不能在合成数据上继续调。
我把这些误判样本写进了 `qa/qa-grid9.js`，工程师可以直接拿去当回归用例。

### 🟢 BUG #4 · 低 · 禁网守卫的盲区与死代码

**先说结论：守卫本身是有效的**（这一点工程师没夸大，我反向验证过）。

我用15 个恶意样本喂 `scanContent()`，**全部被捕获**：
```
require('http') / require('node:http') / require('https') / require('node:https')
require('net') / require('node:net') / require('dns') / require('node:dns')
require('tls') / net.connect() / fetch() / XMLHttpRequest / WebSocket
child_process / 双引号 / 带空格 / node: 前缀
```
`src/` 全树扫描：**0 命中**。`src/` 中零 `Math.random`。
所以**「一个从不报警的守卫」这个风险不成立**。

**但守卫有 5 个盲区**（我用绕过样本实测）：

| 绕过手法 | 是否捕获 | 风险 |
|---|---|---|
| `const m='ht'+'tp'; require(m)` | ❌ 未捕获 | 动态 require。静态扫描的本质局限 |
| `import http from 'http'`（ESM） | ❌ 未捕获 | 项目是 CJS，当前风险低 |
| `globalThis.fetch` | ❌ 未捕获 | 可发起请求 |
| `require('undici')` | ❌ 未捕获 | undici 是**真实出站能力**，Node 内置 |
| `process.dlopen(...)` | ❌ 未捕获 | 可加载原生模块 |

**外加一处死代码**：`ALLOWED_BUILTINS`（`net-guard.js:114`）被导出但
**从未在守卫逻辑里被引用**（我读源码确认，`scanContent` 里没有任何地方用它）。
白名单形同虚设 —— 它给人「有白名单机制」的错觉，实际是摆设。

**修复建议**：
- `FORBIDDEN_PATTERNS` 补：`undici` / `node:undici` / `globalThis.fetch` /
  `process.dlopen` / `process.binding` / ESM `import ... from 'http'`
- 要么真正用上 `ALLOWED_BUILTINS`（做「允许清单」而非「禁止清单」），
  要么删掉它 —— **留着比删掉更坏，因为它造成虚假的安全感**

### 🟡 BUG #5 · 中 · 「坑15守卫」在它要防的场景面前是绿的

工程师报告 §6 特别强调：
> 「第 15 条特别值得记录……必须有测试守着。现已有 determinism.test.js 的两条守卫。」

**我实测这条守卫在它声称要防的场景下不会红。**

**复现步骤**（我实际改过真实配置文件，跑完已完整恢复，md5 已核对）：
```bash
# 在 fgui.config.json 的 diff 段：
#   删除 maxShapeRatioFactor，加入过期键 maxShapeRatioDelta
$ node --test test/unit/determinism.test.js
```
**结果**：`✔ ★ 配置默认值与代码内默认值一致` —— **绿灯通过**。

**根因（自证循环）**：
守卫断言 `config.diff.maxShapeRatioFactor === 1.6`，但它拿到的 `config` 是
`loadConfig()` **与内置默认值深合并后**的对象。配置文件里删掉这个键，
内置默认会把它补回来，`k in config.diff` 仍为 `true` —— **断言永远成立**。

守卫实际能抓的只有两种情形：
- ✅ `grid9` 段多出代码不认的未知键（我实测会红）
- ✅ 已覆盖段的**数值**与内置默认不一致

而工程师报告里描述的坑15 恰恰是「**旧键名残留 + 新键名缺失**」——
这个守卫**防不住**。这是「守卫测试本身是假绿」的典型案例：
**它检查的对象已经被默认值补全了，因此无法区分「配置正确」与「配置缺失」。**

**覆盖缺口**：守卫只覆盖 `grid9` 段（完整）+ `diff` 段（单向，11 个硬编码白名单）。
`search` / `normalize` / `psd` / `asset` 段**完全无守卫**（我grep 确认零断言）。

**修复建议**：守卫必须读**原始配置文件**（`JSON.parse(fs.readFileSync(...))`），
而不是合并后的对象：
```js
const raw = JSON.parse(fs.readFileSync(configPath, 'utf8'));
// 断言 raw 的键集合 === defaultConfig() 的键集合（逐段递归）
```
这样「配置里少一个键」才会红。并把 `grid9` 段的检查推广到全部 6 个段。

### 🟡 BUG #6 · 中 · `npm test` 这个命令本身是坏的

**实测**（同一份代码，同一台机器）：
```bash
$ node --test test/unit test/e2e            # ← package.json 里 npm test 用的写法
ℹ tests 2
ℹ pass 0
ℹ fail 2                ← ❌ 报2 个失败

$ node --test "test/unit/*.test.js" "test/e2e/*.test.js"
ℹ tests 199
ℹ pass 199
ℹ fail 0                ← ✅ 实际全绿
```

Node v24 的 `--test` 对**目录参数**的处理方式变了：它把目录当成 2 个「测试项」，
而不是递归收集其中的测试文件。

**这是最讽刺的一个问题**：验收标准第 1 条是「`npm test` 全绿」。
**按 README/报告里写的命令跑，会看到 2 个失败。**
工程师报告里写「199/199 通过」—— 他一定是用了 glob 或 IDE 跑，
**但交付给别人的入口是坏的**。任何按 `npm test` 验收的人都会得到红色。

**修复建议**：`package.json` 改为
```json
"test": "node --disable-warning=ExperimentalWarning --test \"test/**/*.test.js\""
```

**IR bbox 断言的有效性**：
