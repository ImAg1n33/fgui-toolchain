## 1. 原始需求复述

> **开源说明**：本 PRD 保留原始撰写视角。「客户/合作方」指提出真实需求的某游戏团队 UI 程序，
> 文中「小 Q」为沟通代号，非真实姓名；效果草图与 PSD 均为合成样本，未包含任何真实美术资产。

客户（某游戏团队 UI 程序，沟通代号「小 Q」）现状：**「工作流还是手动拼 UI 的，我可能好几天都不写代码，就一直在拼 UI」**。

已有的二次开发方案：AI 看效果图 → 识别布局与素材层级 → 按素材名前缀去目录翻素材 → 调 `fgui-agent-bridge` 逐个命令拼 FGUI。

已验证的三个 slowdown 根因：

1. **往返成本**：高度依赖图像识别，逐个调用 MCP 工具，模型推理 + 工具往返开销大，「感觉还没他手拼快」。
2. **素材命名混乱**：画师切图**完全没有命名规范**，实际文件名形如 `矩形1`、`矩形11`、`特效`、`图层129`、`图层249(1)`、`组1200拷贝`。
3. **多状态界面**：同一界面多个状态 = 多张效果图 = 多份 PSD，重复素材在第二份 PSD 里被合并、不再分层，只能对着效果图硬猜。

## 2. 产品定义

### 2.1 产品目标（一句话）

> **让 AI 先「看懂项目已有的东西」，再动手拼 UI —— 把 FairyGUI 拼装从「逐个对象 × 逐次工具调用」的视觉重建，改造成「存量资产复用 + 差异驱动生成」的批量增量构建。**

这句话拆成三句可验证的产品承诺：

- **看懂已有资产**：能自动回答「这张切图在工程里叫什么名字」「这个弹窗上一版是怎么做的」「哪些东西可以直接复用」。
- **批量而非逐个**：把「200 个显示对象 = 200 次 MCP 往返」压缩为「1 次规划 + ≤5 次桥调用」。
- **增量而非重建**：多状态界面产出 1 个组件 + N 个 controller gear，而不是 N 个独立页面。

### 2.2 定位与差异化

业界「AI 生成 UI」普遍在做**从零视觉重建**（截图 → 代码）。我们的场景不是这个：

- 有现成的、量很大的历史 FGUI 工程（可复用组件、已登记素材、包结构）。
- 有规范的 FairyGUI 工程纪律（`STANDARDS.md` 已固化成 lint）。
- 真正的时间黑洞是「翻几百张无名切图」+「在编辑器里一个个拖对象」。

所以差异化是 **Reuse-First（复用优先）**，而不是 **Vision-First（视觉优先）**。这条判断决定了整个技术选型（详见 §5.2 路线选择）。

### 2.3 User Stories（站在小 Q 一天的真实流程上）

> **US-1（上午 10:00，收到新需求）**
> 作为 UI 程序，我希望工具先扫一遍公司历史 FGUI 工程和公共切图目录，直接告诉我「弹窗底框、关闭按钮、标题底、领取按钮这四个件在 `Common` 包里已经有了，直接引用」，这样我不用先去网上翻两小时旧界面。

> **US-2（上午 10:40，拿到画师新切的 217 张图）**
> 作为 UI 程序，我希望工具把这 217 张无名切图（`矩形1`、`图层249(1)`、`组1200拷贝`……）自动建成可搜索的索引，并按「我要的槽位」给我 Top-5 候选缩略图，我只需要在缩略图上点选确认，映射关系会被缓存下来，这样我不用在资源管理器里一张张点开看。

> **US-3（下午 13:30，拿到邮件弹窗两张 PSD）**
> 作为 UI 程序，我希望工具对比状态 A（普通邮件）和状态 B（带奖励）两份 PSD，直接告诉我：「弹窗背景 / 装饰边框 / 关闭按钮 / 标题 → 完全复用 `MailPanel`；邮件正文 / 发件人 / 有效期 → 位置调整，走 `relation`；3 个奖励物品 → 新增 `GList` + `ItemCell`；领取按钮 → 新增，走 `Button.grayed` 双态」，并直接生成一个 `MailDetail` 组件 XML 草稿，而不是让我从空组件开始拖 180 个对象。

> **US-4（下午 15:00，第一次生成结果不完美）**
> 作为 UI 程序，我希望生成的组件 XML 在写入磁盘之前就已经过了项目规范 lint（10 种合法标签、6 位色、九宫格不越界、`exported` 不漏），并且原始文件有备份、可以一键回滚，这样我最坏情况就是「退回手工」，不会把线上工程搞坏。

> **US-5（第二天，同类界面又来一个）**
> 作为 UI 程序，我希望第二次遇到相似界面时，工具能直接告诉我「`MailDetail` 与本次目标相似度 0.72，建议基于它做增量修改」，这样第二个界面的耗时应该明显低于第一个。

## 3. 需求池

> 编号 `R1..R5` 为模块编号；`P0/P1/P2` 为交付优先级。
> **优先级与团队 lead 建议的差异及理由见 §3.6。**

| 模块 | 名称 | 优先级 | 可离线验证 | 依赖 |
|---|---|---|---|---|
| R1 | 素材索引器（Asset Indexer） | **P0** | ✅ 完全可 | 无 |
| R2 | PSD 解析器 → Design IR | **P0** | ✅ 完全可 | R1（可选） |
| R3 | 差异分析器 → ChangePlan | **P0** | ✅ 完全可 | R2 |
| R4 | FGUI 组件 XML 生成 + lint + 事务写盘 | **P1** | ✅ 完全可 | R3、已有 FGUI 工程副本 |
| R5 | 现场验证包（Field Verification Kit） | **P1** | ❌ 必须现场 | R4 |

> **为什么 R2/R3 也是 P0（与建议不同）**：R1 单独确实能省翻图时间，但**产品价值的天花板**取决于差异分析。客户最痛的「好几天不写代码」根因是多状态/多版本界面重复劳动，只有 R3 能直接消灭它。R1 独立可用但只是「省两小时」，R1+R2+R3 才是「省两天」。因此把「离线可跑通的最小闭环」整体定为 P0：**切图 → PSD → 差异 → ChangePlan（JSON，人可读可改）**。这个 P0 阶段**不需要碰 FairyGUI，也不需要 C# 环境**，开发者本机 100% 能跑通、能写单测。

### R1 · 素材索引器 —— P0

**问题**：217 张切图，文件名无意义。翻找 = 主要体力活。

**功能需求**

| ID | 需求 | 优先级 |
|---|---|---|
| R1-F1 | 递归扫描切图目录（PNG/JPG/WebP），生成 `assets.db`（SQLite） | P0 |
| R1-F2 | 每张图提取特征：像素宽高、宽高比、**alpha 包围盒**（内容不透明区域）、透明像素占比、平均主色（k-means 3~5 色）、`pHash`（64bit DCT）、边缘密度 | P0 |
| R1-F3 | **九宫格候选性启发式判定**（见下） | P0 |
| R1-F4 | 生成 contact sheet：单文件 HTML，所有缩略图以 `data:` URI 内嵌，网格排列，支持按尺寸/主色/文件名筛选 | P0 |
| R1-F5 | 三通道检索（见下），输出 Top-K 候选 + 置信度 | P0 |
| R1-F6 | 人工确认 → 写入映射缓存 `map.json`（语义槽位 → 文件绝对路径 + 特征指纹），二次运行直接命中，**零重算** | P0 |
| R1-F7 | 对无命名的图给出**建议名**（基于尺寸/主色/形态，如 `panel_bg_720x420`、`icon_item_64x64`），但**只建议不重命名** | P1 |
| R1-F8 | 增量扫描：目录 mtime + 文件 hash 双重校验，只处理新增/变更 | P1 |

**检索三通道（关键设计）**

小 Q 现有做法是「按给定素材名前缀去目录找素材」——失败，因为文件名没规范。但有一个被忽略的事实：

> **PSD 图层名通常与导出的切图文件名同名**（画师在 `图层129` 上画，切出来也叫 `图层129.png`）。

所以：

| 通道 | 做法 | 覆盖占比（预估） | 成本 |
|---|---|---|---|
| **Ch-1 精确同名** | IR 里的图层名（或语义槽位名）== 文件 basename（忽略大小写/全半角/去 `(1)` 副本后缀），命中后用**像素尺寸校验**（图层 bbox 与图片尺寸一致 ±2px） | **预计 50~70%** | 毫秒级，零歧义 |
| **Ch-2 尺寸+结构** | 用「图层 bbox 尺寸 vs 图片尺寸」硬过滤 + 透明边界形状相似度打分（IoU） | 20~30% | 秒级 |
| **Ch-3 pHash 视觉** | 64bit pHash 汉明距离 + 主色直方图距离 + 宽高比硬过滤 | 兜底 10~20% | 秒级 |

排序权重：`score = 0.5·Ch1 + 0.3·Ch2 + 0.2·Ch3`，Ch-1 命中直接短路置顶。**结果必须带置信度并显式标注「这条是同名确定的 / 这条是猜的」**，猜的进人工确认队列。

**九宫格候选性判定（R1-F3，差异化项）**

直接把 `STANDARDS.md §2.7` 的规则算法化，输出三档：`CAN_9GRID` / `SINGLE_AXIS_ONLY`（胶囊形，输出建议 `scale9grid="r,0,w-2r,h"`）/ `NEVER`（圆、放射、对角高光）。判定依据：四角实心度、中部行/列的像素方差、边缘曲率。

> 这条是「别人做不出来、上游 lint 只做越界检查不做适用性检查」的差异化：工具在**生成阶段**就阻止「给胶囊按钮切常规九宫格」这类已被记录过的事故。

**离线可验证性**：100%。开发者本机有 Node + 图片 + PSD 副本即可跑通全部功能与单测。

### R2 · PSD 解析器 → Design IR —— P0

**问题**：现在只对着效果图做，没有结构信息，等于蒙眼拼。

**功能需求**

| ID | 需求 | 优先级 |
|---|---|---|
| R2-F1 | 用 `ag-psd`（Node 库，与 Bridge 同栈）解析单份 PSD：图层树、每层 bbox 绝对坐标、旋转、透明度、可见性、混合模式、分组结构 | P0 |
| R2-F2 | 文本图层：抽出文本内容、字号、颜色、字体、对齐（对齐方式 → FGUI `align`） | P0 |
| R2-F3 | 智能对象 / 切片（slice）信息：若 PSD 内含导出切片，一并抽出（**这是最准的素材-图层对应关系来源**） | P0 |
| R2-F4 | 产出 `design_ir.json`：**扁平化图层列表 + 父子关系 + 绝对坐标**，每层带 `id / name / bbox / type / visible / opacity / text? / source_rect?` | P0 |
| R2-F5 | **合并图层显式标记**：被合并的组打 `merged: true`，并输出 `lost_info` 警告条目进人工确认队列（对应「第二份 PSD 里重复素材被合并、没分层了」） | P0 |
| R2-F6 | 输出**可视化校验图**：把 IR 的 bbox 画在效果图上（单文件 HTML + SVG），让人一眼看出解析对不对 | P0（成本极低、价值极高，强烈建议做） |
| R2-F7 | 支持多份 PSD 一次解析（状态 A / 状态 B / 历史版本） | P0 |

**Design IR 草案 Schema**

```jsonc
{
  "version": "1.0",
  "source": { "psd_path": "...", "canvas": { "w": 1280, "h": 720 }, "dpr": 1 },
  "layers": [
    {
      "id": "L012",
      "name": "矩形11",            // 画师原名，可能是"图层129"
      "parent": "L008",             // null = 根
      "type": "raster",             // raster | text | group | smartobject | slice
      "bbox": { "x": 120, "y": 88, "w": 720, "h": 420 },
      "rotation": 0,
      "opacity": 1,
      "visible": true,
      "blend": "normal",
      "merged": false,              // true = 该组已被画师合并，信息不可恢复
      "slice": { "name": "mail_bg", "rect": [120, 88, 720, 420] },  // 若有
      "text": {                      // type=text 时
        "value": "恭喜获得奖励",
        "fontSize": 28, "color": "#F5E6C8", "align": "center",
        "font": "SourceHanSans-Bold"
      }
    }
  ],
  "warnings": [
    { "code": "MERGED_LAYER_GROUP", "layer": "L030", "msg": "组『组1200拷贝』被合并，展开为 3 层扁平内容" }
  ]
}
```

**离线可验证性**：100%。单测 = 用邮件弹窗两份 PSD 做黄金样本，断言 bbox/层级/文本抽取正确。

### R3 · 差异分析器 → ChangePlan —— P0

**这是产品的核心，也是「差异驱动」的落点。**

**问题**：状态 A / 状态 B 两份 PSD，凭人眼对比 180 个对象 = 一整天。

**匹配四级（从强到弱）**

| 级别 | 依据 | 说明 |
|---|---|---|
| L1 | `slice.name` 完全一致 | PSD 内切片名一致 = 同一素材，最强证据 |
| L2 | 图层名归一化后一致（去 `(1)`/空格/全半角/大小写） | 画师命名习惯一致时的强证据 |
| L3 | **图像内容 pHash + 尺寸 + 位置** | 名字被合并/改了就靠这个兜底 |
| L4 | 上述均不命中 → 判定 `INFERRED`，进人工确认队列，**默认按"新增"处理但明确标注"不确定"** | 宁可多问一句，不要猜错 |

**差异分类与 FGUI 映射**

| 差异类型 | 判定条件 | 映射到 FGUI 的处理 |
|---|---|---|
| `REUSE` | 两边同一素材（L1/L2 命中） | 直接引用，**零新增节点** |
| `MOVE` | 同素材，bbox 变化但尺寸不变 | 优先 `relation`（`sidePair`）；相对关系复杂时用 `gearXY` |
| `RESIZE` | 同素材，尺寸变但比例不变 | 九宫格（先过 R1-F3 适用性检查）；不合适 → `gearSize` |
| `RESTYLE` | 同位置同尺寸，颜色/透明度变 | **不生成新图**，用运行时 `color` + `alpha`（6 位色，`STANDARDS.md §3`） |
| `ADD` | 仅 B 有 | 新建节点；重复结构 → `GList` + 独立 Cell 组件 |
| `REMOVE` | 仅 A 有 | 默认 `visible=false` 或移入 `stash/`，**不直接删** |
| `INFERRED` | 匹配不确定 | 进人工确认队列，未确认前不写入 |

**结构建议（自动生成，写入 ChangePlan 供确认）**

- 重复结构检测（同一父级下 3+ 个 bbox 等距等尺寸的同类节点）→ 建议 `GList`（`layout="flow_hz"` + `defaultItem` + 独立 Cell），依据 `STANDARDS.md §2` 「禁止在页面里平铺 N 份 cell」。
- 复用件检测（多页面/多状态反复出现的同一素材组合，如「弹窗底 + 边框 + 关闭按钮」）→ 建议抽 `common/PanelFrame` 子组件。
- 与存量 FGUI 工程做相似度比对（特征：引用的图片集合 + 文本节点 + 布局结构相似度）→ 命中则输出 `REUSE_EXISTING_COMPONENT` 建议，指向具体组件名。
- 双态按钮 → 建议 `Button mode="Check"` 或 `grayed` 切换，而不是做两份。

**ChangePlan 草案 Schema**

```jsonc
{
  "version": "1.0",
  "task": { "name": "MailDetail", "base_pkg": "Mail", "target_pkg": "Mail" },
  "sources": { "psd_base": "state_A.psd", "psd_target": "state_B.psd", "fgui_project": "D:/work/mail-ui" },
  "summary": { "reuse": 4, "move": 3, "resize": 1, "restyle": 2, "add": 6, "remove": 1, "inferred": 2 },
  "diffs": [
    { "op": "REUSE", "slot": "popup_bg", "from": "Common/PanelFrame", "match_level": "L1",
      "evidence": "slice 'mail_bg' 一致", "confidence": 1.0 },
    { "op": "ADD",  "slot": "reward_list", "node": "L041",
      "fgui_strategy": { "type": "list", "layout": "flow_hz", "default_item": "MailItemCell",
                         "item_count": 3, "item_size": [96, 96], "gap": 12 } },
    { "op": "ADD",  "slot": "btn_claim", "node": "L052",
      "fgui_strategy": { "type": "button", "extention": "Button", "states": ["grayed", "normal"] } },
    { "op": "INFERRED", "slot": "icon_3", "candidates": ["图层249(1).png", "矩形11.png"],
      "reason": "合并图层导致匹配不确定", "default_if_unconfirmed": "skip" }
  ],
  "open_questions": ["状态B 的奖励物品是否为 3 列 flow_hz？", "领取按钮灰置条件由代码控制还是图控？"]
}
```

**离线可验证性**：100%。邮件案例就是这个模块的黄金测试样本。

### R4 · FGUI 组件 XML 生成 + lint + 事务写盘 —— P1

**问题**：即使前面全对，最后写 XML 这一步也可能把工程写坏（上游已记录：重复属性报错、8 位色渲染成纯蓝、`exported` 漏了发布静默丢包、`ui://` 包 id 非 8 位吃掉 itemId 首字符）。

**功能需求**

| ID | 需求 | 优先级 |
|---|---|---|
| R4-F1 | IR + ChangePlan → 组件 XML。**增量优先**：先读现有 XML 做 diff，只改变化节点，禁止整份重写（否则人工修正点位数会爆炸，直接失去「省时间」的意义） | P0 |
| R4-F2 | 全量遵守 `STANDARDS.md`：displayList 仅 10 种合法标签、`extention` 仅 8 种合法值（拼写就是 `extention`）、颜色 6 位 + `alpha`、`ui://` + 8 位包 id、`scale9grid` 读 png IHDR 对账、`exported="true"` 齐全、id 序列 `b000NN`/`c000NN`、语义命名（禁 `n0/n1`）、单组件对象数 ≤80 告警 | P0 |
| R4-F3 | 复用上游 `lint_components.mjs` / `check_publish.mjs`，在其规则基础上**新增**：`INFERRED` 未确认节点不得写入、九宫格适用性检查（R1-F3）、胶囊形单轴专用切法提示 | P0 |
| R4-F4 | **事务化写盘**：写临时文件 → lint → 通过 → 备份原文件（`.bak.<ts>`）→ 原子替换 → 失败自动回滚；提供 `rollback` 子命令 | P0 |
| R4-F5 | **安全写入序列**：默认「编辑器关闭状态」下写盘；写完输出 `reload_hint`（提示需重启编辑器 / 触发 refresh），**严禁在编辑器开着时手写 `package.xml`**（`STANDARDS.md §3` 明确会被内存态覆盖） | P0 |

## 5. 关键技术决策

### 5.1 复用上游哪些东西 / 新建哪些东西

**事实基线（已核实源码）**

- 上游 `fgui-agent-bridge` v0.4.1：插件层 25 个命令；MCP 层注册 **26** 个 tool。
- `write_component`（直写组件 XML）**只存在于插件层，未暴露到 MCP**；上游 v0.4.0 已**主动放弃**该路线（commit 原文：「拼界面不再把整份组件 XML 交给 write_component」），改为逐个调官方编辑器接口。
- **不存在** `build_ui_from_plan` / `apply_ui_plan` 类批量接口（源码 0 命中）——需新建。

**决策**

| 能力 | 决策 | 理由 |
|---|---|---|
| 26 个单步 MCP tool | **直接复用，不重写** | 已实测稳定，桥接层已解决多实例/端口/最小化等一堆脏活 |
| 26 个 tool 的**编排与批量化** | **新建**（本地编排器，不改上游） | 核心增量：把 N 次往返压成 1 次规划 + ≤5 次调用 |
| `write_component` | **不使用、不复活** | 上游已判定该路线失败；我们走 R4「离线生成 XML + lint + 事务写盘」，但在**编辑器关闭时**写盘，规避 `OpenDocument` 不可用与内存态覆盖问题 |
| 批量命令 `apply_ui_plan`（插件层新增） | **P2 可选**，不阻塞 P0/P1 | 因为它依赖 `OpenDocument` 打开组件，而该 API 在上游编辑器构建里不可用；先不做，等现场探测确认可用后再上 |
| `lint_components.mjs` / `check_publish.mjs` / `STANDARDS.md` | **直接继承 + 扩展** | 规范已固化成机器检查，是资产不是负债 |

### 5.2 写盘路线选择（三选一 → 选 C）

| 路线 | 做法 | 优点 | 致命问题 |
|---|---|---|---|
| A. 逐命令调编辑器 API | 每个对象一次 `insert_object` | 官方 API、支持撤销、内存态一致 | **就是现在慢的原因**。200 对象 = 200 次往返，还依赖不可靠的 `OpenDocument` |
| B. 插件层新增批量命令 | `apply_ui_plan(change_plan)` 一次事务执行 | 快 | 仍需编辑器在线；仍需打开组件文档（`OpenDocument` 不可用）；编辑器卡死 = 全批失败；本机无法验证 |
| **C. 离线生成 XML + lint + 事务写盘** ✅ | 生成器产出 XML → lint → 备份 → 原子替换 → 重启编辑器 | **完全离线可验证**（开发者本机就能跑测试）；一次性写入无往返；lint 前置把事故挡在前面；失败零成本 | 需要「编辑器关闭时写盘」，多一次重启（重启成本 ~3s，可接受） |

**选 C。** 决定性因素是**开发者本机没有 FGUI 环境**：只有「离线能生成 + 离线能 lint」这条路，我们才可能在没有客户配合的情况下持续迭代。B 路线每写一行都要等朋友在公司机器上帮忙试。

### 5.3 必须继承为硬约束的上游踩坑清单

| 坑 | 约束 |
|---|---|
| `App.docView.OpenDocument` 静默返回 null / 抛 "overload is stripped by unity" | **不使用 OpenDocument**。R5 探测脚本如实上报是否可用，但产品不依赖它 |
| `ScreenCapture` 系列被裁，且 Jint 中「truthy 但不可调用」，`typeof`/真值守卫拦不住，必须 try/catch 实调 | **不使用 `screenshot`**。改 OS 级截屏（R5-F5） |
| `#RRGGBBAA` 运行时只取后 6 位（`#000000c8` → 纯蓝） | 颜色只用 6 位 + `alpha="0.x"` 属性，生成器**强制**此规则，lint **阻断** |
| 免费版 `batchmode` 被 `CheckProLicense` 拦截 | 不走 batchmode，只走桥 + 插件 |
| 编辑器窗口最小化会暂停主循环 | 保留插件 `runInBackground=true`；R5 Runbook 提醒「不要关闭编辑器」 |
| `CreateComponentItem` 的 `path`/`extentionId` 未用时必须传 `null` 而非 `""` | 若未来走 B 路线，参数一律 `null` |
| `package.xml` 编辑器开着时手写会被内存态覆盖 | R4-F5 写盘序列强制「先关编辑器」；R4-F6 默认不允许改 `package.xml` |
| 读盘成功 ≠ 编辑器能打开（`read_component` 只是 `File.ReadAllText`） | R5 强制「lint → 重启 → refresh → `read_component` 抽查 → publish → 对账」完整序列 |

## 6. 明确不做什么（范围边界）

| 不做 | 理由 |
|---|---|
| ❌ 自研视觉大模型 / 训练识别模型 | 素材命名混乱的问题用「同名通道 + 特征检索 + 人工确认」解决，成本低一个数量级，效果够用 |
| ❌ 复杂多 Agent 陪审系统 | 无 FGUI 环境下单链路都难验证，多 Agent 会把验证成本乘以 N |
| ❌ 做独立 FGUI 编辑器 | 已有一个能用的编辑器；我们的价值在「生成 + 校验」，不在「编辑」 |
| ❌ 一开始就支持所有复杂状态 / 动画（Transition、Gear 全量） | P0/P1 只做 `gearDisplay`/`gearXY`/`gearSize`/`gearText`；Transition、粒子、3D、骨骼动画明确排除 |
| ❌ 向量数据库（Milvus/Qdrant/pgvector） | 初期数据量（几百到几千张图）用 SQLite 元数据 + 本地二进制特征文件足够；pHash 走汉明距离，必要时配 BK-tree |
| ❌ 自动下载蓝湖切图 | 蓝湖需要登录态/鉴权，且是公司资产链路；P0 只支持「本地已有切图目录」。批量下载列入 P2 且需先确认可行性与合规 |
| ❌ 自动改文件命名 / 批量重命名切图 | 会破坏美术工作流与已有引用；只给建议名（R1-F7） |
| ❌ 自动 `publish` 到游戏工程 | 保留人工确认闸门；工具只 publish 到临时目录并出对账报告 |
| ❌ 接管运行时 UI 逻辑（GList 的 itemRenderer、按钮事件） | 只生成结构，不生成业务逻辑代码；渲染逻辑位置标注为 TODO 交回给小 Q |

| Q15 | 领取按钮的「条件显示」是**代码控制**还是**图控**？这决定 IR→XML 时要不要生成 `grayed` 双态或 controller gear |
| Q16 | 你更想要哪种交付形态：本地 CLI（灵活、要记命令）、还是本地网页（点点就行、但要起服务）？（我默认 CLI + 单文件 HTML 确认页，因为零构建、便于文件传递） |
