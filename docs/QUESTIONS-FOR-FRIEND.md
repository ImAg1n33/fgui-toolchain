> **用途**：我们正在帮你做一套「FGUI 自动化拼 UI」工具。工具本身已经写好并跑通了，但**有些答案只有你/画师能给**——答错方向会导致返工，所以想先问清楚再往下做。
> **怎么用**：按「第一批 → 第二批 → 第三批」顺序答。**第一批 6 个问题，10 分钟能答完，但决定了后面所有事**。答不上来的直接写「不知道/待确认」，不用勉强。
> **编号说明**：标题里 `Q7` 这种是**我们内部的编号**（和交接文档对应，方便我们追踪），你在意的是问题本身，不用记编号。
> **为什么问这些**：每个问题后面都写了「为什么问」和「你的答案会改变什么」。

## 一、第一批：6 个问题（最高杠杆，10 分钟）

### Q1 · 你的 FairyGUI 编辑器具体版本号是多少？

**为什么问**：不同版本的编辑器，组件 XML 的合法写法、`ui://` 资源引用的格式、`extention` 扩展名的合法取值都可能有差异。我们生成的 XML 必须严格匹配你的版本，否则要么被编辑器拒绝打开，要么打开后缺东西。

**你的答案会改变什么**：决定我们生成 XML 时用哪套规则。版本不知道，我们只能按「通用规则」猜，**猜错的后果是生成一堆编辑器打不开的文件**。

**怎么答**：编辑器菜单里找「关于 / Help → About」，把版本号抄给我。类似 `1.x.x` 这样的。

---

### Q2 · 你们工程的 `package.xml` 里，包 id 是稳定的 8 位吗？

**为什么问**：`ui://` 这种资源引用的格式是 `ui://包id/资源名`。如果包 id 不是 8 位（比如 6 位），会吃掉资源名的第一个字符——这不是推测，上游项目记录过一次真实事故：**27 张图 + 组件静默丢失**，最后查出来就是包 id 位数不对。

**你的答案会改变什么**：决定我们生成 `ui://` 引用时的校验规则。如果是 8 位就按标准来；如果不是，我们要为你们的工程做特殊处理。

**怎么答**：随便打开一个包目录下的 `package.xml`，看里面的 `id` 属性，数一下是几位。类似 `id="a1b2c3d4"`。

---

### Q7 · 🔴 画师导出切图时，PSD 里的「切片（slice）」信息会保留吗？

**为什么问**：**这是目前最要紧的一个问题。**

我们做素材匹配的核心思路是「PSD 图层名通常和切图文件名同名」——画师在 `图层129` 上画，切出来也叫 `图层129.png`。这条路子预计能自动匹配 50~70% 的素材，是我们整个方案的地基。

而如果 PSD 里保留了切片信息，匹配准确率会再上一个台阶（切片名是画师主动命名的，比图层名更可靠）。

**但我们的判断是：画师用「导出为」批量导切图时，切片信息很可能不会保留。** 如果确实不保留，我们最强的匹配通道就废了，只能退回到「图层名 + 图像特征」匹配，准确率会明显下降。

**你的答案会改变什么**：
- **如果保留** → 现有方案直接可用，准确率高
- **如果不保留** → 我们要么调整匹配策略，要么**提前和画师约定导出时保留切片**

这不是「差一点」的问题，是**可能要改设计**的问题。所以想最早确认。

**怎么答**：这个可能要问画师，或者你自己导一次试试——用 Photoshop 打开一个 PSD，看「文件 → 导出 → 导出为」或者画师用的导出方式，导完之后新 PSD/导出目录里还能不能看到切片标记。也可以直接问画师：「你导切图的时候切片会一起导出吗？」

### Q17 · FairyGUI 里胶囊按钮（左右圆头的那种）九宫格的标准写法是什么？

**为什么问**：九宫格（scale9grid）的作用是让按钮拉伸时圆角不变形。胶囊形按钮的切法很特殊——它只有左右两个圆头，中间是直的，所以**不能按常规九宫格切**，要用「单轴」切法：中心区横向占满整个高度、圆头整个落在左右边栏里。

我们算出来的建议格式是 `scale9grid="r,0,w-2r,h"`，其中 `r` 是圆角半径、`w`/`h` 是图宽高。**但我们只验证了算术是对的，没有办法验证 FairyGUI 编辑器是否真的接受这个格式。**

**你的答案会改变什么**：如果格式不对，我们给所有胶囊按钮的九宫格建议**全是错的**——后果是圆头按钮一拉宽就出现月牙形残影。这是整个工具里**最容易造成线上事故的一处**。

**怎么答**：两种方式任选：
1. 你在编辑器里给一个胶囊按钮配过九宫格的话，把 `package.xml` 或组件 XML 里 `scale9grid` 那一行抄给我
2. 或者告诉我你们项目里是怎么写的，有没有专门的规范文档

---

### Q18 + Q19 · `displayList` 里到底有哪 10 种合法标签？`extention` 有哪 8 种合法值？

**为什么问**：我们做了一个「规范检查」模块，用来在生成 XML 之前先自查——比如不允许出现拼错的标签、不允许非法的扩展名、颜色必须用 6 位等。这些规则必须是**你们项目实际用的那套**，否则会出现「合法的组件被我们拦住」这种误报，比不检查还糟糕。

目前我们按 FairyGUI 的通用集合在假设（比如 `image`/`text`/`list`/`component`/`graph` 这些），**但不确定是不是你们版本的那 10 个**。

**你的答案会改变什么**：决定检查规则的具体清单。猜错的后果是**误拦你们的合法组件**，你们会觉得「这工具怎么老拦我」。

**怎么答**：如果有现成的规范文档（我们听说你们有 `STANDARDS.md`？）直接发我最省事。或者你随手打开一个现有组件的 XML，把里面出现过的标签名念给我，我自己去重。

---

### Q6 · 你们工程的包 id / 资源名，有用中文或者特殊字符的吗？

**为什么问**：你们的切图文件名本来就没规范（`矩形1`、`图层249(1)`、`组1200拷贝`），我们已经做了归一化处理。但想确认一下包名和资源 id 会不会有中文、空格、括号之类——这会影响我们做文件路径和资源引用时的转义处理。

**你的答案会改变什么**：决定我们要不要做额外的路径转义。不做的话遇到特殊字符会生成错误的 `ui://` 引用。

**怎么答**：大致描述一下就行，比如「包名都是英文小写，资源名偶尔有中文」。

## 二、第二批：需要看一眼工程或问一下人（约 20 分钟）

### Q3 · 能否给一份脱敏的 FGUI 工程副本？

**为什么问**：这是**没有它就无法验证任何东西**的一项。我们现在所有的测试都是用程序合成的假素材跑的一一功能能跑通，但**合成素材证明不了在你们真实的乱命名切图上好不好使**。

**需要什么**：不需要完整工程，也不需要真实美术资源。只要有：
- 包目录结构（`assets/`、`*.xml`、`package.xml` 这些）
- 2~3 个你们**真实做过**的组件 XML（比如邮件弹窗、商店格子、背包物品格都行）
- 对应的一组切图（**不用命名规范，越乱越真实**，但请确认已脱敏/可外传）

**如果涉及公司保密**：可以在你们公司机器上跑，我们给一套脚本，你跑完只回传「结果报告」，不回传素材本身。我们全程不联网、不上传任何图片。

**你的答案会改变什么**：决定我们能不能从「代码能跑」推进到「在真实场景下好不好用」。这是验收的唯一依据。

---

### Q4 · 你们组件 XML 的实际缩进和换行风格是什么？

**为什么问**：我们做的是「增量修改」——只改变化的节点，不重写整个文件。这样人工修改的点位会少很多（这是省时间的关键）。但要做到增量 diff 不破坏你们原有格式，缩进风格必须和你们一致。

**你的答案会改变什么**：影响 diff 的友好度。如果风格不匹配，每次改动都会带上大量无关的格式变化，你们 review 起来很痛苦，还不如手改。

**怎么答**：打开一个组件 XML 看几眼——是一个 Tab 缩进？两个空格？四个空格？属性是一行一个还是全挤一行？

---

### Q5 · 编辑器开着的时候，直接手改组件 XML（不是 package.xml）会被内存态覆盖吗？

**为什么问**：我们计划用「离线生成 XML → 检查 → 备份 → 替换」的方式写文件，这比逐个调编辑器 API 快得多，也不会被编辑器卡死影响。但前提是**写盘的时候编辑器不能开着**，否则编辑器内存里的旧内容会把我们的改动覆盖掉。

我们已知 `package.xml` 编辑器开着时手写一定会被覆盖。但**组件 XML 不确定**——如果也会被覆盖，写盘流程必须严格「关编辑器 → 写 → 重启」。

**你的答案会改变什么**：决定写盘流程要多严格。如果组件 XML 也会被覆盖，我们每次写完都要重启编辑器（约 3 秒，可以接受）；如果不会，流程能更顺。

**怎么答**：试一次就知道——编辑器开着，在外部改一个组件的 XML 保存，回编辑器看有没有提示「文件已外部修改」，或者看内容有没有变。

---

### Q22 · 你们的切图有 1x / 2x 倍图混用吗？

**为什么问**：我们用「图层尺寸 vs 图片尺寸 ±2px」来验证素材是否匹配。这个容差是按 1x 设计的。如果同时存在 2x 图，一张在 PSD 里是 96×96 的图，实际文件可能是 192×192——按 ±2px 校验会全部判为不匹配。

**你的答案会改变什么**：决定尺寸校验要不要支持倍率推断。如果有 2x，我们要改校验逻辑，否则素材匹配会大面积失准。

**怎么答**：看切图目录里有没有明显成 2 倍关系的文件，或者直接说「全是 1x」/「有 2x」。

---

### Q8 · 差异分类的人工标注对照表，你能提供吗？

**为什么问**：我们的差异分析会输出「该复用哪些、该新增哪些、该调整哪些」。要验证这个判断准不准，需要一份**人工标注的标准答案**来对账。你们做过邮件弹窗，正好是最合适的样本。

**需要什么**：普通邮件和带奖励邮件这两个状态，你人工列一下：
- 哪些元素是两个状态完全一样的（背景/边框/关闭按钮/标题…）
- 哪些只是位置变了
- 哪些是新增的（奖励物品、领取按钮…）

**你的答案会改变什么**：这是我们验证「差异分析准确率 ≥90%」的唯一依据。没有它，我们只能说「代码逻辑对」，不能说「结论对」。

---

### Q20 · 语义命名的禁用词，你们有具体范围吗？

**为什么问**：我们检测到节点名是无意义的画师原名（`图层301` 这种）时会给出提示，建议改成语义名（`btn_close` 这种）。但我们目前用的是宽松规则——只拦「明显无语义」的。想确认你们项目有没有明确的禁用词表或命名规范。

**你的答案会改变什么**：决定提示的严格程度。太松会漏提示，太严会把你们合法的短名（比如 `bg`、`n1`）也拦掉，变成噪声。
